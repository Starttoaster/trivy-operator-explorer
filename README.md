# Trivy Operator Explorer

A web UI for viewing reports generated by the [Trivy Operator for Kubernetes](https://github.com/aquasecurity/trivy-operator). It aggregates vulnerability scans, config audits, RBAC assessments, exposed secrets, compliance reports, and more across multiple clusters into a single dashboard.

## Architecture

Trivy Operator Explorer uses an **agent/server** model. This replaces the previous approach of installing the explorer independently in every cluster.

- **Agent** — runs in each Kubernetes cluster. It watches Trivy Operator CRDs (VulnerabilityReports, ConfigAuditReports, etc.), normalizes the data, and periodically pushes a `ClusterReport` to the central API via `POST /api/v1/sync`.
- **API server** — runs in a central cluster. It receives reports from agents over mTLS and writes them to PostgreSQL.
- **Frontend** — runs alongside the API server in the central cluster. It reads from PostgreSQL and serves the web UI.

All communication between agents and the API server is secured with mutual TLS (TLS 1.3). The frontend is exposed via an Ingress; the API server typically stays internal.

## Prerequisites

- [Trivy Operator](https://github.com/aquasecurity/trivy-operator) installed in each cluster you want to monitor.
- A PostgreSQL database accessible from the central cluster.
- TLS certificates for mTLS between agents and the API server (a CA, server cert/key, and client cert/key signed by the same CA).

## Install

### Server (central cluster)

The server chart deploys both the API server and the frontend.

```bash
helm upgrade --install --create-namespace \
  --repo "https://starttoaster.github.io/trivy-operator-explorer" \
  -n trivy-explorer \
  trivy-operator-explorer-server \
  trivy-operator-explorer-server \
  --set database.dsn="postgres://user:pass@db-host:5432/trivy?sslmode=disable" \
  --set tls.secretName=trivy-api-tls
```

The TLS secret must contain `ca.crt`, `tls.crt`, and `tls.key`. See `chart/trivy-operator-explorer-server/values.yaml` for all available options including Ingress, replica counts, and resource limits.

### Agent (each monitored cluster)

```bash
helm upgrade --install --create-namespace \
  --repo "https://starttoaster.github.io/trivy-operator-explorer" \
  -n trivy-explorer \
  trivy-operator-explorer-agent \
  trivy-operator-explorer-agent \
  --set clusterName="my-cluster" \
  --set api.url="https://trivy-api.example.com:8443" \
  --set tls.secretName=trivy-agent-tls
```

| Value | Description |
|---|---|
| `clusterName` | Unique identifier for this cluster (required) |
| `api.url` | URL of the central API server (required) |
| `syncInterval` | How often to push reports (default `5m`) |
| `tls.secretName` | Secret with `ca.crt`, `tls.crt`, `tls.key` for mTLS (required) |

## Generating mTLS Certificates

The API server and agents authenticate each other using mutual TLS. You need a shared CA, a server certificate for the API, and a client certificate for each agent. The steps below use `openssl` to create these.

### 1. Create a Certificate Authority

```bash
openssl genrsa -out ca.key 4096
openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
  -subj "/CN=trivy-explorer-ca" -out ca.crt
```

Make sure to save `ca.crt`!

### 2. Generate the API server certificate

Replace the SAN (`DNS:` / `IP:`) entries with the hostname or IP that agents will use to reach the API server.

```bash
openssl genrsa -out server.key 4096
openssl req -new -key server.key -subj "/CN=trivy-explorer-api" -out server.csr

openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -sha256 -days 3650 \
  -extfile <(printf "subjectAltName=DNS:trivy-api.example.com") \
  -out server.crt
```

Make sure to save `server.key` and `server.crt`!

### 3. Generate an agent client certificate

Repeat this for each agent, giving each a distinct CN.

```bash
openssl genrsa -out agent.key 4096
openssl req -new -key agent.key -subj "/CN=trivy-agent-my-cluster" -out agent.csr

openssl x509 -req -in agent.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -sha256 -days 3650 -out agent.crt
```

Make sure to save `agent.key` and `agent.crt`!

### 4. Create Kubernetes secrets

In the **central cluster** (for the API server):

```bash
kubectl -n trivy-explorer create secret generic trivy-api-tls \
  --from-file=ca.crt=ca.crt \
  --from-file=tls.crt=server.crt \
  --from-file=tls.key=server.key
```

In each **agent cluster**:

```bash
kubectl -n trivy-explorer create secret generic trivy-agent-tls \
  --from-file=ca.crt=ca.crt \
  --from-file=tls.crt=agent.crt \
  --from-file=tls.key=agent.key
```
